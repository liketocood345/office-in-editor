## 已核实的承载机制线索

公开示例通过 WebSocket 发送目标窗口区域、浏览器类型及窗口信息，并提供 OLE 和完整嵌入模式。核心承载运行时没有在本轮获得对应完整源码；仓库中的 MIT 文件不能替代随附商业运行时的授权。[仓库及说明](https://github.com/wangzuohuai/WebRunLocal/tree/c53d55bfe57f1b4251d57dcccbce70bb65f5995d)

其通用 EXE 接口明确提供 `Wrl_AppletAlpha`，用于网页菜单临时覆盖原生窗口时调整透明度；另提供独立 WebView2 网页叠加。由此可以确认厂商也需要专门处理原生窗口与 HTML 的层级问题，但这些公开接口尚不足以证明 Cursor 自有 HTML 菜单可直接正确合成。[接口文档](https://github.com/wangzuohuai/WebRunLocal/blob/c53d55bfe57f1b4251d57dcccbce70bb65f5995d/Net/ExeWebApplet.txt)

配置中的 `ElectronExe` / `ElectronTitle` 体现了浏览器适配需求；支持 Electron 的声明尚未成为已实测的 Cursor 标签页支持。[配置](https://github.com/wangzuohuai/WebRunLocal/blob/c53d55bfe57f1b4251d57dcccbce70bb65f5995d/Net/ZbaConfig.json)

静态 PE 检查确认相关文件是 Windows 原生 PE，浏览器模块导出 `ElectronWindowAdd` 等适配入口。导出和导入表只证明模块包含这些入口或依赖，不能代替调用轨迹，也不能据此证明使用了全局键鼠钩子。REA 的 PE 资源检查可以运行；本机没有配置完整原生反编译引擎，因此没有声称已还原闭源实现。

## 自写组件已经做到哪里

新增 [原型源码](../experiments/native-surface-bridge/README.md)，采用 C++20，编译为 `oie-native-surface.dll`，提供 C ABI。它是开发实验，不是独立办公软件，也没有接入当前生产 VSIX。

已实现原生父窗口归属校验、按标签创建真实子窗口槽、代次隔离、原生客户区布局、无变更布局去重、显式原生覆盖层排序和带占用检查的释放。父窗口的移动由 Windows 原生关系完成，无需按屏幕坐标持续追赶。

以MSVC构建，开启`/W4 /WX`，23项合成窗口检查通过。检查覆盖真实Win32父子关系、两个标签的隔离、代次拒绝、覆盖窗口顺序、布局去重、占用状态下拒绝销毁及显式清理。这里验证的是原生窗口状态和命中顺序，没有验证Chromium像素合成、中文输入法、Office保存或40ms交互目标。

它不能把现有 DOM 节点变成 HWND。当前实现只接受宿主自己拥有的原生覆盖窗口；浏览器/IDE 适配层、输入法与加速键、Office 崩溃恢复以及真实浏览器的覆盖层合成仍未实现。合成窗口测试不等于 Word 或网页验收。

## 真正补齐冲突的组件应是什么

它应是一个**浏览器/IDE 宿主参与的原生表面桥**，通常由以下部分组成：

| 部分 | 职责 | 适合语言 |
| --- | --- | --- |
| 标签适配器 | 创建、切换、分屏、关闭标签，传递会话身份 | TypeScript |
| 宿主原生提供者 | 在真正的 UI 进程分配槽，并让菜单、焦点和覆盖层参与同一承载契约 | C++；Rust也可通过Win32及宿主接口实现 |
| 原生桥 | HWND生命周期、DPI、布局、原生覆盖层、失效通知 | 本次原型为C++ DLL |
| 共享 Core 与 Office 加载项 | OLE、文档身份、保存、选区、聊天路由和MCP | 继续使用现有C#实现 |

关键不在语言。运行于扩展进程的本机 DLL，并不自动获得浏览器 UI 进程的合成能力。普通 localhost 服务只提供控制通道；完整实现还需要可用的浏览器/IDE 原生提供者。原型把这部分接口具体化了，不能据此宣称缺失的提供者已经存在。

本轮未把未通过验证的后端设成默认编辑器，没有安装原型到 Cursor，也没有推送仓库。
